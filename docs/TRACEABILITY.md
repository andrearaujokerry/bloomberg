# TRACEABILITY — every requirement mapped to a status, a mechanism and a test

This is the BRIEF §7 deliverable and milestone I13 of [WORKPLAN.md](./WORKPLAN.md) §15. It maps all
**158** requirement ids in [REQUIREMENTS.md](./REQUIREMENTS.md) to exactly one status.

## How to read this

**This is the WP-15 regeneration, graded against code that exists.** The previous version opened by
saying "the repository currently contains the design spine and the work plan; `packages/` does not
exist yet", and every one of its 158 rows therefore graded a promise and its assigned test name.
Fifteen work packages later that sentence is false. Five packages and more than 250 test files exist,
the server boots, and the four-panel seeded workspace loads in a browser. So every row below
was re-derived from the repository rather than edited in place.

| Status | Means |
| --- | --- |
| **implemented** | A named mechanism exists in `packages/` **and** a named test that exists on disk covers the requirement's clause. Both are cited by path. If only one can be cited, the row is not implemented. |
| **partial** | The mechanism exists but is narrower than the requirement. The `note` says what exists and what the gap is, in one sentence each. |
| **out-of-scope** | Ruled out, with the reason quoted from [BRIEF.md](./BRIEF.md) §1 where BRIEF names the id. Six rows (REG-02, REG-08, OPS-01, ANAL-05, ANAL-06, NEWS-05) are out of scope for a reason BRIEF §1 does not state verbatim; those notes say so rather than pretending a quote exists. |

### Five rules this regeneration applied, because each one moved rows

1. **Every cited path was checked against disk.** A script extracted all 151 backticked paths from
   the previous version and stat'd them: **45 did not exist.** Some were renames the packages made
   (`core/test/analytics/bond/price.test.ts` shipped as `analytics/bond.price.test.ts`;
   `integration/entitlements/evaluator.test.ts` as `evaluator.int.test.ts`); some were tests that
   were never written (`test/perf/plant.perf.test.ts`, the sixteen `test/fuzz/*.fuzz.test.ts`,
   `core/test/no-io.test.ts`, `integration/pit.fundamentals.test.ts`,
   `functions/PORT.attribution.test.ts`, `web/test/chart/events.test.ts`). Every citation below is a
   path that exists today. Where WORKPLAN.md or TESTING.md names it differently, the note gives both
   spellings and says which one is the file.
2. **A Playwright spec is never the sole evidence for a row.** `packages/e2e` is excluded from
   vitest entirely and `npm test` never runs it, so a spec's evidence has to be asked for by name
   (`npm run test:e2e`). The seven specs of WP-15's acceptance table were landing in
   `packages/e2e/tests/` while this file was regenerated and were unrun at the time; `smoke.spec.ts`,
   which predates them, had been rewritten off the WP-01 scaffold it no longer described. **They have
   since been run, and twice: 39 tests, identical both times — 30 green and 9 `test.fail`s, 3.3 min a
   run** (2026-09-26, Google Chrome, against `bloomberg_e2e_17` copied from the seeded template). The
   nine are not tolerances: each RUNS on every suite and must fail, so the day one is fixed
   Playwright reports "expected to fail but passed". BUILD_STATUS.md lists them.

   The rows below were graded before that run and are deliberately **not** regraded on it. Every
   citation here is still a vitest path, which is the stricter reading of this rule and does not ask
   a reader to trust a browser run they cannot reproduce from `npm test`. What the run changes is
   that several rows are now under-credited rather than over-credited: TERM-01, TERM-02, TERM-03,
   TERM-04, TERM-05, TERM-08, FUNC-03, ENTL-05 and DATA-10 each have a green spec that asserts
   seeded values by name (`330.27`, `CIK 0000320193`, `7,585.75`, a CSV compared cell for cell
   against the screen). Promoting them is one deliberate pass over nine rows, not a silent edit, and
   it is the next thing this document owes.
3. **A green test over code no source file imports is not evidence.** `chart/scales.ts` is 761
   lines that `grep -rn "from './scales" packages/web/src/` does not find a single importer for;
   `chart/renderer.ts` and `chart/layers.ts` carry their own copies of the same geometry. Its 29
   assertions are green about arithmetic the product never executes (BUILD_STATUS.md), so CHRT-03 is
   re-pointed at the tests over the code that draws.
4. **A mechanism the composed process does not run is at best partial.** `packages/server/src/index.ts`
   still defers five startup steps to packages that are merged — the field dictionary (3), the
   function-registry consistency check (4), the universe search snapshot and its ETag (5), the
   ingest leader lock and scheduler (8), the usage-event and DQ writers and the 1 s staleness sweep
   (9) — so `GET /api/v1/health` reports `status: "degraded"` and `scheduler: false`. That moved
   FUNC-04 and OPS-03 out of `implemented`: their writers exist, are tested, and are not armed in
   the running server. See [What the running application does not do](#what-the-running-application-does-not-do).
5. **Ten implemented rows were sampled and their cited tests actually run.** Output is in
   [Verification sample](#verification-sample). A row citing a test that does not exist, or does not
   assert the clause, is worse than a row marked partial.

Two SCOPE rows and the four BIZ rows have no executable check; their `test` column reads
`n/a (document decision)`.

**A correction to the previous version's own arithmetic:** it carried two summary tables, one
totalling 64 / 67 / 27 and one whose bold row said 66 / 65 / 27. The per-subsystem table summed to
64 / 67 / 27, which was the right pair; the 66 was a transcription error and the sentence built on
it ("two of the 66 implemented rows…") inherited it.

## What the running application does not do

Three things a reader of the tables above would otherwise have to infer. Each is measured against
the composed app, not read off a comment.

**1. Five startup steps defer to packages that are already merged.** `src/index.ts` names them in a
`PENDING_STEPS` table and logs one warning each: the field dictionary and its field-id validation
(3, WP-03/WP-11), calendars and the function-registry consistency check (4, WP-08), the universe
search snapshot and its ETag (5, WP-09), the ingest leader lock and scheduler (8, WP-07), and the
usage-event and DQ writers plus the 1 s staleness sweep (9, WP-08/WP-13). So `GET /api/v1/health`
answers 200 with `status: "degraded"` and `scheduler: false`, which is the truth rather than a
defect — but it is what moved FUNC-04 and OPS-03 to partial, and it means **no ingest job runs in
the running server at all**: the application serves the seeded universe and nothing refreshes it.
The access-log writer (ENTL-04) and the alert engine (NEWS-07) are the two that *are* wired, and
`index.ts` says why each is where it is.

**2. The window keyboard dispatcher is built and never attached** (TERM-06, TERM-07, and FUNC-03's
missing key path). Driven in real Chrome on QM with a `role="gridcell"` focused, five documented
keys produce zero `/api/v1` requests, no focus movement and no change to the command draft. Stated
once so it is not re-derived: `keyboard/dispatcher.ts` is complete, but `KeyboardHost.region()`,
`screenBindings()`, `capturesTypedText()` and `screenAction()` all need the focus model
`keyboard/focus.ts` defines, and the only place a `FocusState` and `collectFocusNodes(spec.body)`
both exist is `shell/Panel.tsx`, which keeps them in private component state. So `Panel` must
publish its focus and its merged bindings — a callback prop, or a focus slice on `state/panels.ts` —
before the composition root can build a host at all. Re-deriving the focused node's kind from the
DOM is not an alternative: it is a second focus model that will disagree with the first at exactly
the moments the first was written to get right. The remaining question is a design decision rather
than a wiring one: what stage 4 (`regionKey`) does when the grid, the chart, the form and the
command line already answer their own keys at the element.

**3. Two widgets have no registered component.** `Composer` (MSG-01) leaves MSG without a message
composer and FXC without an editor grid; `Sparkline` (CHRT-01) leaves DES's `rate` variant, ECO and
EE with a placeholder where a small series belongs. Both are recorded in `widgets.tsx` with their
reasons, and `Sparkline`'s is a provenance rule rather than an omission: the node passes
`{points:[{t,v}], fmt}` with no `provIdx` on any point, and DATA-10 forbids drawing a number whose
source cannot be named. Closing it means the three screens passing the provenance index they
already hold, not a change to the registry. `packages/web/test/app/App.test.tsx` pins the current
state with an inverted assertion ("leaves MSG and FXC on the WP-12 placeholder") that fails the day
a component is registered, which is the correct shape for a gap that is meant to close.

## Highest-risk partials

Ranked by what breaks if the gap is not closed before the first external user.

2. **SEC-04 (encryption at rest / mTLS / customer-managed keys)** — zero design coverage, no test,

3. **FUNC-04 and OPS-03 (the two writers that are not armed)** — one line of composition each,

4. **QA-01 (a golden that is wrong, and an oracle that is missing)** — `HP.price.json` asserts a

6. **QA-03 / OPS-03 (reconciliation that cries wolf)** — most values have exactly one source, so

   that is fixed the queue trains its reader to ignore it.
7. **DATA-07 / DATA-08 source gaps that reach the screen** — consensus estimates are structurally

10. **NFR-01 / QA-04 (capacity unknown, and now known to be unmeasured)** — the system degrades

## Open questions

1. **Does a mechanism without a test count as implemented?** This file still says no, which keeps
   SEC-04, REG-06, REG-07 and QA-06 partial. Six rows that the previous version pushed into `partial`
   for this reason have since acquired tests, which suggests the strict reading was the useful one.
2. **Does a mechanism the running process does not execute count as implemented?** This file says no,
   which is what moved FUNC-04 and OPS-03. The alternative reading — "the code and its test exist,
   the composition is a separate concern" — is defensible, and it is exactly the reading under which
